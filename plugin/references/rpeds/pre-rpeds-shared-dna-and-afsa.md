# PRE–RPEDS Shared DNA and A.S.F.R.E.E Adaptive Functional Situational Adapter

## Identity model

PRE Standalone and RPEDS are peer manifestations of one jointly evolved roadmap capability. They share a common kernel but retain separate first-class host-facing identities, extensions and release/adoption receipts.

- PRE Standalone remains independently usable outside A.S.F.R.E.E.
- RPEDS remains the native A.S.F.R.E.E roadmap workstream under M00. Its identity and original four modules are preserved.
- The shared PRE–RPEDS DNA kernel contains common roadmap semantics, contracts and validated reusable methods.
- Host extensions retain environment-specific workflow, procedures, integration and policy. They are not discarded merely because a similar shared-core feature exists.

This is a merger of capabilities and learning lineage, not a product rename or wholesale replacement.

## Shared-kernel composition

The shared kernel contains R0–R9 lifecycle semantics; objective hierarchy; phase/milestone/work-item data model; typed dependencies; multi-dimensional delivery, acceptance, verification, outcome and risk measures; evidence requirements; hard-gate semantics; revision-safe adaptation; process journal and audit; assurance/closure; capability learning; next-action recommendation; continuation prompt contracts; and release compatibility.

## Preserved RPEDS-native composition

1. Roadmap Architecture Planner — A.S.F.R.E.E case-derived objective/phase decomposition and M00 handoff.
2. Progressive Development Manager — A.S.F.R.E.E iteration and work-state coordination with engineering handoff.
3. Continuous Evaluation Engine — local checkpoint scheduling and evidence preparation for O12 judgment.
4. Adaptive Roadmap Optimizer — host-aware replan proposal using A.S.F.R.E.E O03–O06/O11/O12 inputs when triggered.

These modules may consume new PRE capabilities, but remain named and maintained as RPEDS modules. New shared-core capabilities do not silently remove host-specific methods.

## Two-way evolution

A validated host-neutral improvement from PRE can be proposed for RPEDS and other registered hosts. A validated RPEDS improvement can be proposed for the shared kernel and PRE Standalone. Candidate contributions are classified as SHARED_DNA, HOST_EXTENSION, HOST_ADAPTATION, HOST_SPECIFIC or QUARANTINED_OR_REJECTED. Only SHARED_DNA is eligible for common release. Keep provenance, digest, origin lineage, tests, license/reuse basis and adoption receipts. Never propagate host-only SOP, authority, credentials, private case data or sensitive records.

## Adaptive Functional Situational Adapter (AFSA)

Before a shared update or capability is applied, AFSA resolves the exact host profile, policy/SOP references, authority, data boundaries, tool/runtime capabilities, audit sink and rollback reference.

Precedence: binding law/platform constraints → host-approved SOP/security/privacy → host decision rights/delegation → shared PRE–RPEDS kernel → convenience. The adapter changes how a shared function is applied, not its canonical meaning. A host-specific extension is not considered obsolete merely because the shared kernel adds a related feature.

Disposition: DIRECT_COMPATIBLE, ADAPTED_COMPATIBLE, HELD_FOR_AUTHORITY, QUARANTINED_OR_REJECTED. Changes to authority, identity, security, privacy, permissions, licensing, data flows, required approvals or non-waivable SOP need host approval. Unknown is not compatible.

## Release event and adoption

Every core release uses an authenticated, immutable event with release identity, version, digest, contract version, compatibility range, provenance, origin lineage and idempotency key. Each host receives a per-release receipt with previous/candidate versions, AFSA disposition, policy refs, CI/tests, PR/commit/deployment, read-back, rollback and final adoption state.

Safe additive non-breaking shared-DNA updates may auto-adopt only through a pre-approved policy and passing host checks. Host extensions and host-only data remain in their host. Material SOP/authority/security/privacy/licensing conflicts are held or gated. The host is not marked adopted until exact manifest/skill/schema/digest read-back passes.

## Existing architecture authority

M00 remains the sole A.S.F.R.E.E case coordinator. O11 retains authorization/security/privacy; O12 retains independent evaluation judgment; O10 retains test execution/verification; O09 retains supported runtime/integration; O07/O08 retain accepted remediation/reconstruction. PRE/RPEDS never self-grants permissions or self-approves.
