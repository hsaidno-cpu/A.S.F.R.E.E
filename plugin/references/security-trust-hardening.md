"# A.S.F.R.E.E P2 Security & Trust Hardening\n\n**Package:** 0.4.0 · **Reference runtime:** 0.2.0 · **P2 overlay:** 0.3.0  \n**Disposition:** local reference implementation tested; production deployment HOLD.\n\n## 1. Purpose and boundary\n\nP2 connects identity, data protection, workload execution and trust infrastructure into one fail-closed chain. The portable plugin remains skills and contracts. The runtime remains a locally reconstructed Python reference implementation. No IdP, KMS/HSM, Redis, WORM vault, SQLCipher build, rootless OCI runtime, gVisor/Kata, host quota agent or cloud tenant infrastructure is provisioned by these files.\n\n## 2. End-to-end trust chain\n\n`OIDC principal + provider-attested MFA → Ed25519 delegated capability → receiving-worker verification → shared atomic replay/revocation → SCIVE policy boundary → tenant-bound encrypted storage → bounded OCI execution → host quota receipt → external WORM receipt → independent human review → release admission`.\n\nA signature alone does not grant authorization. A local folder is not tenant isolation. A generated OCI command is not proof of a sandbox. A local hash chain is not WORM immutability.\n\n## 3. Identity and SCIVE\n\n- OIDC provider conformance requires server-pinned HTTPS issuer, exact JWKS URI and RS256 support. It is a discovery contract probe, not an IdP login service.\n- MFA-sensitive actions require a provider-specific `MFAClaimProfile`, signed attestation bound to issuer/subject/token and fresh `auth_time`. Generic `mfa=true` is insufficient.\n- Ed25519 delegated capabilities bind issuer/source issuer, audience, principal, tenant, action, resource owner/allowlisted attributes, policy, JTI, lifetime, one-time status, scopes, roles and MFA evidence. Worker processes receive public verification keys, never the issuer private signing key.\n- Shared Redis Lua adapters atomically consume one-time JTI and bind physical infrastructure resource IDs to one tenant. Production must use shared durable state; no local-only fallback.\n- SCIVE registry maps every public EvidenceStore, OrchestrationEngine and ChangeManager operation to a unique policy. New unmapped public methods are release blockers. This is a facade contract: production API/MCP adapters must expose only the policy boundary and keep raw services private.\n\n## 4. Encryption and data lifecycle\n\n- `AWSKMSKeyProvider` uses an injected authenticated client for tenant/object/purpose-bound data-key generation, decrypt and re-encryption. No cloud account, workload role or key ARN is configured here.\n- `SQLCipherStore` refuses ordinary SQLite fallback. The tenant DB DEK is KMS-wrapped in a sidecar; WAL/temp/rekey settings and cross-process key initialization coordination are applied where supported.\n- `EncryptedRecordSink` encrypts audit/log records before they reach the backend.\n- `EncryptedStreamFile` encrypts backup/temp streams with AES-256-GCM and authenticates tenant/object/purpose. Plaintext is committed to the approved transactional sink only after the final tag verifies.\n- These adapters do not automatically encrypt arbitrary OS logs, crash dumps, swap, telemetry, CI artifacts or external backup agents. Every data path must be explicitly wired and independently checked.\n\n## 5. Execution\n\n`StreamingRootlessOCIExecutor` drains stdout/stderr incrementally while retaining bounded buffers, records total bytes/truncation, terminates process trees on timeout and requires a signed host quota receipt before spawning. Supported host quota modes are XFS/ext4 project quota, Btrfs qgroup and ZFS dataset. Measuring usage after a process exits is not enforcement.\n\nThe receiving worker verifies delegated capability and policy before dispatching through the rootless OCI preflight. Actual gVisor/Kata execution, seccomp profile deployment, disk quota, hostile workload and container escape tests are NOT_RUN in the current environment.\n\n## 6. Tenant isolation, WORM and admission\n\n- The infrastructure tenant router checks a signed dedicated-database receipt, tenant-specific IAM/network/KMS references, freshness and a mandatory shared atomic backend-resource binding.\n- `AnchoredAccessDecisionRecorder` uses durable outbox events and externally verified WORM receipts with sequence/hash continuity. Its in-memory anchor is test-only.\n- `ProductionAdmissionGate` requires every configured infrastructure control, a signed attestation tied to the exact release commit and an independent signed human review using a separate trust key. Missing, stale, mismatched or unsigned evidence returns `HOLD`.\n\nA signed receipt is evidence supplied by a provider, not proof that the provider is honest. Production requires separate verification of database, IAM, network, key, backup, WORM retention and worker isolation settings.\n\n## 7. Evidence status\n\nUse the following states without upgrading claims by implication:\n- `CONTRACT_DEFINED`: protocol/schema/instruction exists.\n- `CODE_IMPLEMENTED`: reference implementation exists.\n- `LOCAL_TEST_PASS`: named local test passed, including whether provider fakes were used.\n- `LIVE_INTEGRATION_VERIFIED`: actual provider and target environment were exercised.\n- `PRODUCTION_ATTESTED`: exact release commit has trusted infrastructure attestation and independent review.\n- `NOT_CONFIGURED`, `NOT_RUN`, `UNVERIFIABLE`, `HOLD`.\n\nThe current local reference suite passes 135 tests, including 25 P2 hardening tests; the P0 quickstart passes. The tests use injected clients and fakes. They do not prove live IdP, KMS, Redis, WORM/Object Lock, SQLCipher production, OCI/gVisor/Kata, host quota, cloud tenant isolation, hostile workload containment, production concurrency or disaster recovery.\n\n## 8. Production admission checklist\n\n1. Prove the actual IdP issuer, audience, JWKS, RS256 and MFA semantics.\n2. Configure managed signing/KMS/HSM, workload identity, rotation and key audit.\n3. Deploy shared replay/revocation and resource-binding state with TLS, ACL, durability and failover tests.\n4. Run SQLCipher metadata/WAL/temp/rekey/backup/restore tests using real KMS.\n5. Encrypt application logs, SIEM, telemetry, temp, backups and crash/restore paths end-to-end.\n6. Provision rootless OCI + gVisor/Kata + seccomp and hard host quotas; run hostile workloads on the target host.\n7. Prove dedicated tenant DB, IAM, private network, KMS and backup boundaries under concurrent negative tests.\n8. Configure independently administered WORM retention and verify external receipts.\n9. Obtain signed infrastructure attestation and separate independent human review tied to the exact release commit.\n10. Pass the production admission gate and separate change/release approval.\n\nNo secret, private key, credential or token belongs in the repository or chat. Production remains HOLD until evidence is collected and independently reviewed.\n"
