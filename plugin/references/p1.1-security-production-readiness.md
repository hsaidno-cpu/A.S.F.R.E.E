# P1.1 Security-to-Production Readiness Contract

**Status:** architecture and acceptance contract; not a production certification.
**Applies to:** A.S.F.R.E.E M00, O01–O12, SCIVE, reference runtime, tool adapters, and deployment operators.

## 1. Decision model

A.S.F.R.E.E must distinguish these states for every security control:

- `CONTRACT_ONLY`: policy/interface/schema exists; no implementation evidence.
- `REFERENCE_IMPLEMENTED`: local reference implementation exists; provider/runtime may be mocked.
- `LOCAL_TESTED`: tests passed in a named local environment and cover the stated boundary.
- `PROVIDER_INTEGRATED`: real provider account, identity, key service, storage, or host agent is configured and read-back verified.
- `STAGING_VERIFIED`: adversarial, concurrency, failure, restore, and security acceptance tests passed in isolated staging.
- `HUMAN_REVIEWED`: independent security reviewers signed an evidence-based review.
- `PRODUCTION_VERIFIED`: approved deployment, host/provider read-back, monitoring, recovery, and post-deployment tests are evidenced.
- `BLOCKED`, `NOT_RUN`, `UNVERIFIABLE`: preserve these states; never map them to PASS.

A control can have multiple evidence rows, but a weaker state cannot imply a stronger state. A mocked provider test is not a cloud integration. A local unit test is not a tenant-isolation test. A CI green check is not a production verification.

## 2. Identity, MFA and delegated authority

### 2.1 IdP trust
Production identity requires a configured and independently verified IdP. Pin trusted issuer, audience, token type, algorithm allowlist, JWKS origin, TLS policy, key rotation behavior, client identity, and accepted scopes. Validate expiry, not-before, issued-at, subject, authorized party/client, and required claims. Reject token-selected key/JWKS URLs, unsigned tokens, algorithm substitution, issuer/audience mismatch, and untrusted redirects.

Prefer established OAuth/OIDC profiles and token-exchange mechanisms. Record the exact profile and provider configuration. Do not implement a partial JWT parser that silently broadens the accepted token language.

### 2.2 MFA assurance
Do not treat a boolean claim or a bare AMR value as proof of MFA. Maintain an operator-controlled mapping of IdP ACR/AMR values to assurance levels and document which authenticators satisfy each level. Require fresh authentication time for high-risk operations. For privileged access, prefer phishing-resistant authenticators and verify the IdP actually enforces the requested policy.

The evidence must include the IdP policy, claim mapping, a redacted signed-token validation trace, negative tests for stale/wrong assurance, and proof that the relying party rejects claims outside the configured mapping. Never retain bearer tokens in audit logs.

### 2.3 Delegated capabilities
Cross-process delegation must use an asymmetric signature or a standards-based token exchange, not a process-local shared HMAC secret. Bind at minimum: issuer, subject, tenant, audience, action, resource, case/job, actor/delegation chain, issued/expiry times, unique token identifier, key identifier, and scope attenuation.

Enforce signature/key rotation and bounded key refresh; exact audience and resource binding; tenant binding to the target store and execution job; no privilege amplification across delegation hops; expiry, revocation, replay prevention, and use-count semantics; canonical serialization and stable signing input; and fail-closed behavior on unknown key, malformed claims, stale token, or unavailable replay state.

A signed capability is an authorization artifact, not a substitute for policy evaluation. Evaluate current policy at each operation boundary.

### 2.4 SCIVE operation coverage
SCIVE must not accept an actor-name string as authority. Every externally reachable state transition must enter through the authenticated policy facade, including propose change, approve/reject, apply, verify, rollback, recovery/replay, cancellation or administrative override.

Bind proposal digest, exact target/path scope, tenant, baseline, approver, executor, verifier, expiry, and required assurance. Enforce separation of duties; the proposer cannot approve their own high-impact change, and the executor cannot be the sole independent verifier. Re-check policy and baseline immediately before mutation to limit TOCTOU windows. Direct access to an unguarded ChangeManager must be unavailable to production callers.

## 3. Encryption and key custody

### 3.1 Envelope encryption and KMS/HSM
Use a managed KMS/HSM or approved provider to generate and unwrap data-encryption keys. Encrypt payloads with authenticated encryption and bind an opaque tenant/object context. Keep key-encryption keys in KMS/HSM. Support key rotation, rewrap, disable/revoke, disaster recovery, audit trails, availability policy, and tested recovery.

Do not expose raw data keys, access tokens, or KMS credentials to logs, prompt context, or untrusted workers. Provider errors must fail closed where confidentiality or integrity is at risk.

### 3.2 Complete data inventory
Encryption scope must include all sensitive persisted forms, not only artifact blobs:

| Data surface | Required control | Required evidence |
|---|---|---|
| Artifact blobs | Envelope encryption with authenticated context | tamper/context mismatch tests; KMS key version read-back |
| Metadata database | Approved encrypted DB/page-encryption engine | encrypted-at-rest inspection; wrong-key open failure |
| WAL/SHM/journal | Covered by the selected DB encryption mechanism | create/write/checkpoint/reopen tests; no plaintext page spill |
| Temporary files | Memory-backed temp store or encrypted scratch volume | process inspection and disk scan after failure |
| Audit records | Encrypted storage plus integrity/signature chain | tamper, deletion and restore tests |
| Application logs | Redacted structured logs to encrypted sink | secret scan, retention, access policy and key rotation |
| Crash dumps/exports | Disabled or encrypted, scoped, retained minimally | configuration and post-failure artifact inventory |
| Backups/snapshots | Independently encrypted and access-restricted | restore drill with rotated keys and cross-tenant denial |

File permissions, encrypted artifact blobs, and encrypted backups do not prove that live metadata or WAL is encrypted. SQLite WAL may contain live database pages; use a proven database page-encryption implementation or a different managed encrypted database. Do not silently fall back to plaintext when a driver or key service is missing.

### 3.3 Key lifecycle
Define ownership, tenant binding, key hierarchy, rotation interval, revocation, compromise response, backup-key access, break-glass process, KMS availability behavior, and recovery objectives. Test rewrap without plaintext exposure, tenant-context mismatch, key revocation, restore with current/previous key versions, and auditability of key operations.

## 4. Execution isolation and host-enforced quotas

### 4.1 Isolation boundary
A Docker-compatible command, container flag, or mock executor is not proof of isolation. For hostile workloads, provision rootless OCI with gVisor or Kata (or an independently reviewed equivalent) on the actual host. Require non-root host/runtime identity and user namespaces; seccomp and AppArmor/SELinux or an equivalent LSM profile; mount, PID, IPC, UTS and network namespaces; no-network-by-default egress policy; read-only root filesystem, minimal allowlisted mounts and ephemeral workspace; image digest allowlist, non-root workload uid, dropped capabilities; no host socket, device passthrough, privileged mode or inherited secrets; and explicit cleanup on timeout, cancellation, crash and quota breach.

### 4.2 Quota enforcement
The host/runtime boundary, not caller metadata, enforces CPU, memory, PID, process count, wall-clock, disk, I/O, network and output quotas. A host quota receipt must be authenticated and bound to tenant, job, image digest, runtime/host identity, limit set, start/end time, observed usage, exit status, and policy version. Validate it before and after execution; reject stale, forged, mismatched or incomplete receipts.

### 4.3 Streaming output
Read stdout and stderr concurrently while the process runs. Enforce byte limits before buffering, keep a bounded tail or encrypted spill where explicitly configured, and kill the process group at the limit. Do not use unbounded capture followed by truncation. Define total output, per-stream output, log rate, retention and redaction limits.

### 4.4 Hostile-workload test matrix
The staging suite must include CPU loops, memory exhaustion, PID/fork bombs, output floods, large file writes, disk exhaustion, timeout/cancellation, symlink/path traversal, environment/secret leakage, network egress, cross-tenant mount access, process escape assumptions, cleanup, and concurrent jobs. Record image digest, host/kernel/runtime versions, sandbox policy, test outcomes and remaining unknowns.

If Docker/rootless runtime, gVisor/Kata, seccomp/LSM or host quota agent is absent, execution must be BLOCKED or NOT_RUN. Do not downgrade to a weaker executor without explicit risk acceptance and scope restriction.

## 5. External trust infrastructure and tenancy

### 5.1 External audit anchor
A local hash chain only detects some local modifications; it does not prevent an administrator from rewriting the entire chain. Anchor signed checkpoints to a separately administered immutable/WORM store, with tenant/case boundary, monotonic sequence, predecessor hash, timestamp, signing key ID, and retention policy.

After each write, read back the exact object and verify its digest, signature, predecessor and object-lock/retention status. Test deletion, overwrite, reordering, replay, truncation, forked histories, clock skew, partial writes and provider outage. Fail closed or preserve a clearly marked pending-anchor state when policy requires anchoring before further high-risk mutations.

### 5.2 Infrastructure tenant isolation
Application-level query filters and per-tenant folders are defense in depth, not a production trust boundary. Demonstrate isolation at identity, database, object storage, KMS context, encryption keys, network, worker/runtime and backup layers. Select an isolation model (separate account/project, database, namespace, key hierarchy or an explicitly justified combination) and verify it using identities belonging to different tenants.

### 5.3 Concurrency and resilience
Run parallel proposals, approvals, applies, rollback/recovery, duplicate requests, replayed tokens, lease expiry, anchor retries, key rotation and concurrent tenant operations. Verify serializability/idempotency, unique constraints, state transition guards, no lost updates, no cross-tenant reads/writes, and consistent audit sequence. Record tested load envelope and limits; do not extrapolate beyond it.

## 6. Independent human security review

Production release requires a review by a qualified person independent from the builder and proposer. The review record must contain reviewer identity/role, conflict declaration, scope and exclusions, commit/build/provider/runtime identifiers, threat model, test/evidence references, open findings, remediation decisions, residual risks, expiry/review date, approval or rejection, and verifiable signature.

The review template is not evidence of review. AI-generated review text is not a human sign-off. Unresolved critical/high findings block production release unless an authorized risk owner formally accepts a narrowly scoped exception supported by compensating controls.

## 7. Production release gates

| Gate | Minimum evidence | Failure disposition |
|---|---|---|
| G1 Identity & SCIVE | real IdP policy, verified MFA claims, cross-process signature/replay/revocation tests, all SCIVE boundaries covered | HOLD |
| G2 Encryption & key lifecycle | real KMS/HSM, encrypted DB/WAL/temp/log/audit/backup, rotation/restore evidence | HOLD |
| G3 Execution & tenant isolation | rootless OCI + gVisor/Kata, host quotas, bounded logs, hostile workload and cross-tenant tests | BLOCKED/HOLD |
| G4 Trust & oversight | external WORM read-back, infrastructure isolation, concurrency tests, independent signed human review | HOLD |

A release can be PASS_WITH_CAVEATS only when no P0/P1 hard gate remains open and the risk owner accepts clearly bounded caveats. If a mandatory control was not exercised, report NOT_RUN, BLOCKED, or UNVERIFIABLE; do not call it a pass.

## 8. Evidence and acceptance rule

Every claim must map to source/implementation, environment, method, evidence ID, test status, provider version, and limitation. Keep four evidence classes separate: repository code or contract inspected; local unit/integration tests actually run; real provider/host integration verified; and independent human review and approved release.

A test specification is not an executed test. A mocked provider is not a live provider. A passing CI suite does not prove production tenant isolation, KMS custody, WORM retention or sandbox containment.
